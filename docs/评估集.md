# BMW X3 车主手册 RAG 评估集

> 数据源：`docs/x3-2024.pdf`（356 页中文车主手册，2023 版）
> 用途：量化评估 RAG 系统的检索与生成质量（Recall@k / MRR / 答案正确性）
> 原则：**先定义评估集，再照着做系统**——评估驱动开发

---

## 一、为什么先做评估集

| 不先做评估集 | 先做评估集 |
|-------------|-----------|
| 「感觉好像变好了」 | 「Recall@1 从 0.63 提到 0.79」 |
| 改完不知道有没有用 | 每个改动都有数字对照 |
| 面试说不清效果 | 能拿出可验证的证据 |

**这个评估集是项目的「标尺」**——后面每一步优化（切分、检索、重排）都拿它来量。

### D. 拒答题（3 题）★ 最重要

**手册里没有答案**，系统应该**明确说「无法确定」，而不是编造**。

| # | 问题 | 期望行为 |
|---|------|---------|
| 28 | 这辆车在火星上能开吗？ | 拒答：「根据现有资料无法确定」 |
| 29 | 换个轮胎要多少钱？ | 拒答：手册不含价格信息 |
| 30 | 这车和奔驰 GLC 哪个好？ | 拒答：手册不含竞品对比 |

> **为什么拒答题最重要**：这是**防幻觉能力的唯一客观测试**。真实客服场景里，编造答案比说「不知道」危险得多。

## 三、数据结构（转成 JSONL 供评估脚本使用）

评估脚本需要机器可读的格式：

```jsonl
{"id": 1, "question": "胎压数据在哪看？", "ground_truth": "驾驶员侧车门的门柱上", "source_page": 284, "type": "basic"}
{"id": 2, "question": "多久检查一次轮胎压力？", "ground_truth": "每月两次，或长途行车前", "source_page": 284, "type": "basic"}
{"id": 28, "question": "这辆车在火星上能开吗？", "ground_truth": null, "source_page": null, "type": "refuse"}
```

**字段说明**：

| 字段 | 含义 | 用途 |
|------|------|------|
| `id` | 题号 | 定位题目 |
| `question` | 问题 | 喂给系统 |
| `ground_truth` | 标准答案（拒答题为 null） | 判断答案对错 |
| `source_page` | 出处页码 | **标定 gold chunk**（比字符重合准得多） |
| `type` | 题型 | 分类统计 |

**关键优势**：有 `source_page` 就能精确定位「正确答案在手册哪一页」——比在保险项目里用「字符重合度」猜 gold 可靠得多（那里踩过坑）。

---

## 四、评估指标

### 检索层

| 指标 | 含义 |
|------|------|
| **Recall@k** | 正确页面出现在前 k 个检索结果的比例 |
| **MRR** | 正确页面的平均倒数排名（越靠前越高） |
| **拒答率** | 拒答题中，系统正确说「无法确定」的比例 |

### 生成层

| 指标 | 检查什么 |
|------|---------|
| **答案正确性** | 生成的答案与 ground_truth 语义一致 |
| **引用准确性** | 答案引用的页码是否正确 |
| **幻觉率** | 拒答题中编造答案的比例（越低越好） |

## 五、使用方式

```bash
# 1. 建索引后，跑检索评估
python eval/evaluate.py --mode retrieval

# 2. 跑端到端（含生成）
python eval/evaluate.py --mode end2end

# 3. 对比不同方案
python eval/evaluate.py --splitter fixed --mode retrieval   # 固定切分
python eval/evaluate.py --splitter semantic --mode retrieval # 语义切分
```

**预期产出**：
```
=== 检索评估 ===
Recall@1 = 0.72
Recall@3 = 0.93
Recall@5 = 0.97
MRR      = 0.81
拒答率    = 1.00 (3/3)
```
